# Add, Edit and Delete Characters Within a Book Implementation Plan

## Overview

Give a reader a page per book where they can add a character with a name alone in seconds,
then edit or delete it and fill in the description note later as reading progresses.

This is roadmap item **S-02**. It is the slice that makes the reader's notes accumulate, and
its page is the surface S-03's cast view extends.

## Current State Analysis

- **S-01 established every idiom this slice copies** (archived at
  `context/archive/2026-09-09-manual-book-entry/`): native `<form method="POST">` with a
  client-side validation gate, routes reading `formData()` and validating with Zod, failures
  reported as a redirect with `?error=`, and lists server-rendered in the `.astro` page.
  `src/pages/books.astro` and `src/pages/api/books.ts` are the working reference.
- **`PROTECTED_ROUTES` needs no change** — verified: `src/middleware.ts:18` matches by
  `startsWith`, so `["/dashboard", "/books"]` already covers `/books/[id]` and anything
  deeper.
- **The RLS convention is written down and proven executable.** `CLAUDE.md` carries the
  template — table shape, ownership column, index, trigger attachment, RLS, four
  per-operation policies, grant and revoke — and it was dry-run as a `characters` table in a
  rolled-back transaction during F-01, producing four policies and a firing trigger.
- **`public.set_updated_at()` already exists** with `search_path` pinned. It must be attached,
  never redefined.
- **`supabase/tests/rls_books.sql`** asserts isolation in both directions for `books` and is
  the file to extend, per the convention in `CLAUDE.md`.
- **`src/types.ts`** holds the `Book` entity plus `createBookSchema` / `updateBookSchema`;
  `src/db/database.types.ts` is generated by `npm run db:types`.
- **Local dev now points at the local Supabase stack**, so development data no longer reaches
  production and `db:verify-rls` covers the database the app actually uses.

## Desired End State

From `/books`, a reader opens a book and lands on `/books/[id]`: the book's title and author
at the top, an add-character form below it, and the book's cast beneath that. Typing a name
and submitting adds the character — no other field required. Each row can be expanded to
correct the name or fill in the description, or deleted outright. Characters are private per
reader, proven by the same harness that covers books.

Verification: `npm run db:verify-rls` passes with the new characters block including its
negative controls, `npx astro check` and `npm run build` are clean, and a character is
creatable from a name alone on a 375px screen.

### Key Discoveries:

- `src/middleware.ts:18` — prefix matching means no route-protection work in this slice.
- `CLAUDE.md` § Key conventions — the RLS template, already proven executable for a
  `characters` table.
- `src/pages/api/books.ts` — the route shape to copy: guard `locals.user`, create the client,
  read `formData()`, `safeParse`, redirect with the first issue's message on failure.
- F-01's `authorField` pattern (`""` → `null`) is the reason optional text fields work with
  formData without special-casing; `description` reuses it.

## What We're NOT Doing

- **No relationships between characters** — that is S-03, the north star.
- **No events** — FR-005, parked in phase 2.
- **No book status** — FR-009, S-04.
- **No editing or deleting books** — still parked as an S-01 follow-up; this slice adds
  character CRUD only.
- **No `PROTECTED_ROUTES` change** — prefix matching already covers the new routes.
- **No redefinition of `set_updated_at()`** — attach the trigger only.
- **No ownership-by-join policies** — policies check `auth.uid() = user_id` directly, as the
  template does and as three later tables will.
- **No textarea component** — `description` uses the existing `FormField` input. A multi-line
  note component is a later concern; introducing one here would fork the form primitives.
- **No test runner** — unchanged from F-01 and S-01.
- **No deployed-path verification phase** — the deployed cookie → JWT → `auth.uid()` → policy
  path was proven end to end in S-01, and this slice reuses that path unchanged with the same
  policy shape.

## Implementation Approach

Three phases. Phase 1 lands the `characters` data layer and extends the isolation harness, so
the guarantee exists before any UI can write rows. Phase 2 delivers US-02's core: the book
page and an add form that accepts a name alone. Phase 3 completes FR-003's CRUD with inline
edit and delete. Each phase is locally verifiable and revertible.

## Critical Implementation Details

**A forged `book_id` is possible and must be guarded in the route, not the policy.** The
policies check `auth.uid() = user_id` only, so a hand-crafted POST naming another reader's
`book_id` would create a character owned by the poster but pointing at a book they do not
own. It leaks nothing — RLS keeps that row invisible to the book's owner — but it is
referential nonsense. The guard is free: the route must load the book by id anyway to render
or validate against, and that `select` is RLS-filtered, so a book the reader does not own
comes back empty. Treat "book not found" as the rejection path.

**Name-alone submission is the acceptance criterion, not a nicety.** US-02 fails if the form
requires anything beyond a name. Client-side validation must check the name only, and
`createCharacterSchema` must accept a missing or empty `description`.

## Phase 1: Characters data layer and isolation harness

### Overview

Create the `characters` table from the `CLAUDE.md` template, extend the isolation harness to
cover it in both directions, and regenerate the database types.

### Changes Required:

#### 1. Characters migration

**File**: `supabase/migrations/<YYYYMMDDHHmmss>_create_characters_with_rls.sql` (new)

**Intent**: Land the second domain table using the established convention, so isolation and
`updated_at` behaviour are inherited rather than re-invented.

**Contract**: Table `public.characters` following the `CLAUDE.md` template verbatim for
ownership, RLS, the four `authenticated`-only policies, the grant, the revoke and the trigger
attachment. Domain columns: `book_id uuid not null references public.books (id) on delete
cascade`, `name text not null`, `description text` (nullable). Two indexes: the template's
`(user_id, created_at desc)` for the policy predicate, plus `(book_id, created_at desc)`
because every listing query filters by book — an addition to the template, not a substitution.
`set_updated_at()` is attached, never redefined.

#### 2. Characters isolation assertions

**File**: `supabase/tests/rls_books.sql`

**Intent**: Extend the existing harness so the new table is covered by the same command, per
the `CLAUDE.md` rule that every RLS table gets a block here.

**Contract**: A characters block inside the existing transaction, reusing the two fixture
readers and their books. Keeps both directions: reader B cannot select, update, delete or
forge ownership of reader A's characters, and reader A can insert with no `user_id` (proving
`default auth.uid()`), then update and delete their own row with `row_count = 1`. Extends the
closing `raise notice` to name characters. Still ends in `rollback`.

#### 3. Regenerated database types

**File**: `src/db/database.types.ts`

**Intent**: Keep the generated row types in step with the schema, as `CLAUDE.md` requires
after every migration.

**Contract**: Output of `npm run db:types`. Generated file — not hand-edited, and excluded
from lint and prettier already.

### Success Criteria:

#### Automated Verification:

- Migration applies from scratch: `npx supabase db reset`
- Isolation harness passes with the new block: `npm run db:verify-rls`
- Negative control: broaden `characters_select_own` to `using (true)`, confirm
  `npm run db:verify-rls` FAILS, then restore with `npx supabase db reset`
- Positive control: narrow `characters_update_own` to `using (false)`, confirm the harness
  FAILS on the owner-can-update assertion, then restore
- Types regenerate and contain a `characters` row type: `npm run db:types`
- Type checking and build pass: `npx astro check`, `npm run build`
- Linting passes: `npm run lint`

#### Manual Verification:

- Studio shows `characters` with RLS enabled and exactly four `authenticated` policies
- Deleting a book cascades its characters away; deleting a reader cascades both

pause here for manual confirmation from the human that the manual testing was successful

## Phase 2: Book page and add a character

### Overview

The book's own page with an add-character form that accepts a name alone, and the book's cast
listed beneath it. This is US-02.

### Changes Required:

#### 1. Character types and commands

**File**: `src/types.ts`

**Intent**: Add the shapes the route and form share, following the `Book` precedent so the
validator and the compile-time type cannot drift.

**Contract**: A `Character` entity mirroring the migration's columns one-to-one, plus
`createCharacterSchema` (name required after trim, length-capped; `description` optional and
`""`-normalised to null, reusing the `authorField` pattern) and `updateCharacterSchema` (both
optional, rejecting an empty update), with `CreateCharacterCommand` / `UpdateCharacterCommand`
inferred from them. `id`, `user_id`, `book_id` and timestamps are never accepted from a
client.

#### 2. Create-character route

**File**: `src/pages/api/books/[id]/characters.ts` (new)

**Intent**: Accept the add-character post for one book, validate it, and return the reader to
the book page.

**Contract**: `export const POST: APIRoute` plus `export const prerender = false`. Guards
`locals.user`; loads the book by `params.id` through the RLS-filtered client and treats an
empty result as rejection (see Critical Implementation Details); reads `formData()`; parses
with `createCharacterSchema`; inserts `{...parsed, book_id}` with no `user_id`. Redirects to
`/books/<id>` on success and to `/books/<id>?error=<encoded>` on failure.

#### 3. Add-character form island

**File**: `src/components/characters/AddCharacterForm.tsx` (new)

**Intent**: A form that submits from a name alone, so US-02's 30-second bar is achievable on
a phone.

**Contract**: Default-exported component taking `bookId: string` and
`serverError?: string | null`. Renders `<form method="POST" action={`/api/books/${bookId}/characters`}>`
with a required `name` field and an optional `description` field, mirroring `AddBookForm`'s
structure and reusing `FormField`, `SubmitButton` and `ServerError` from
`@/components/auth/`. **Client-side validation checks the name only** — no other field may
block submission.

#### 4. Book page

**File**: `src/pages/books/[id].astro` (new)

**Intent**: The per-book surface: identify the book, add characters, read the cast. S-03
extends this page rather than adding another.

**Contract**: Loads the book by `Astro.params.id` through the RLS-filtered client; renders
Astro's 404 response when it comes back empty, so another reader's book id is
indistinguishable from a missing one. Renders title and author, then
`<AddCharacterForm client:load />`, then the book's characters ordered `created_at desc` with
name and description, plus an empty state. Reads `?error=` from `Astro.url.searchParams`.
Matches the cosmic glassmorphism of `books.astro` and needs no horizontal scrolling at 375px.

#### 5. Link from the collection

**File**: `src/pages/books.astro`

**Intent**: Make the new page reachable — today the collection list is inert text.

**Contract**: Each list row's title becomes a link to `/books/<id>`. No layout or query
change.

### Success Criteria:

#### Automated Verification:

- Type checking passes: `npx astro check`
- Production build succeeds: `npm run build`
- Linting passes: `npm run lint`
- Formatting is clean on the files this phase touched (`npx prettier --check` on them; do NOT
  run `npm run format`)
- Isolation harness still passes: `npm run db:verify-rls`

#### Manual Verification:

- **A character is added from a name alone** — description left empty, submitted, appears in
  the list. This is US-02's acceptance criterion
- The whole add flow — open book, type name, submit — completes in under 30 seconds on a
  phone-sized viewport
- At 375px the page needs no zooming and scrolls only vertically
- A character added with a blank description renders without an empty-string artifact
- An empty or whitespace-only name is refused client-side, with no page load
- Clicking a book in `/books` opens that book's page
- Requesting another reader's book id returns 404, not an empty page or an error trace
- With JavaScript disabled the add form still submits

## Phase 3: Edit and delete a character

### Overview

Complete FR-003's CRUD: correct a name, fill in a description later, or remove a character —
all without leaving the book page.

### Changes Required:

#### 1. Update-character route

**File**: `src/pages/api/characters/[id].ts` (new)

**Intent**: Apply an edit to one character and return to its book page.

**Contract**: `POST` plus `prerender = false`. Guards `locals.user`, parses with
`updateCharacterSchema`, updates by `params.id` — RLS restricts the update to the reader's own
row, so no ownership check is duplicated in code. Reads `book_id` from the updated row (or a
hidden form field) to build the redirect back to `/books/<book_id>`.

#### 2. Delete-character route

**File**: `src/pages/api/characters/[id]/delete.ts` (new)

**Intent**: Remove one character. A separate route because HTML forms cannot issue DELETE, and
a hidden `_action` field would conflate two operations.

**Contract**: `POST` plus `prerender = false`. Guards `locals.user`, deletes by `params.id`
under RLS, redirects to the book page. A delete affecting zero rows is not an error — it means
the row was not the reader's, which RLS already handled.

#### 3. Inline edit and delete controls

**File**: `src/pages/books/[id].astro`

**Intent**: Put correction where the character is, with no navigation, keeping the no-JS
baseline.

**Contract**: Each character row gains a `<details>` disclosure containing a native POST form
to `/api/characters/<id>` with `name` and `description` prefilled and a hidden `book_id`, plus
a separate small POST form to `/api/characters/<id>/delete`. Pure HTML disclosure — no island,
no client JavaScript.

### Success Criteria:

#### Automated Verification:

- Type checking passes: `npx astro check`
- Production build succeeds: `npm run build`
- Linting passes: `npm run lint`
- Formatting is clean on touched files
- Isolation harness still passes: `npm run db:verify-rls`

#### Manual Verification:

- Editing a character's name updates the row and returns to the same book page
- Filling in a description on an existing character works — the incremental-note flow US-02
  describes
- Deleting a character removes it from the list
- Edit and delete both work with JavaScript disabled
- A second account cannot edit or delete the first account's character by id — attempting it
  changes nothing

**Implementation Note**: After completing this phase and all automated verification passes,
pause here for manual confirmation from the human that the manual testing was successful.

## Testing Strategy

### Unit Tests:

None — no test runner, unchanged from F-01 and S-01.

### Integration Tests:

- `npm run db:verify-rls` extended with the characters block, both directions.
- Two controls in Phase 1 rather than one: a too-broad policy must fail the check, and a
  too-narrow policy must fail it too. The second exists because negatives alone pass happily
  when a policy is over-restrictive.

### Manual Testing Steps:

1. `npx supabase start` (Docker must be running), then `npx supabase db reset`.
2. `npm run db:verify-rls` — expect a clean pass naming books and characters.
3. `npm run dev`, sign in, add a book, open it from the collection.
4. Add a character with a name only; confirm it appears.
5. Add a second character with a description; confirm both render.
6. Expand a row, correct the name, submit; confirm the change and the return to the page.
7. Add a description to the name-only character.
8. Delete a character.
9. Narrow the viewport to 375px and repeat steps 4 and 6.
10. Disable JavaScript and repeat steps 4, 6 and 8.
11. Sign in as a second reader; confirm the first reader's book id 404s and their characters
    are invisible.

## Performance Considerations

Negligible at this scale. The listing query filters by `book_id` and orders by `created_at
desc`, which the added `(book_id, created_at desc)` index serves directly; the RLS predicate
is served by the template's `(user_id, created_at desc)`.

## Migration Notes

One new table, no data to migrate. Rollback is deleting the migration file and running
`npx supabase db reset` locally; `characters` rows are development data only. The remote
schema needs `npx supabase db push` when this slice deploys — the two databases are distinct
now, so that step is no longer implicit.
